# Cop 別の一致状況

[README の表](../README.ja.md#cop-別の一致状況)は、2026-10-08 に Ruby 4.0.7 上の RuboCop 1.89.0 と CLI 出力を全項目で比較して再生成しました。**登録 609 Cop、発火 606 Cop、完全一致 603 Cop** です。登録・被覆・正確性を分けて測っています。実プロジェクトの結果は [CONFORMANCE.md](../CONFORMANCE.md) に記録しています。

## 入力と比較

本家 spec の記録には、609 の登録名に対応する 42,596 入力・1,551 設定群があります。両 CLI が最後まで検査できたのは 42,435 入力・1,545 設定群です。本家の spec helper が受け付ける null の `EnforcedStyle` を CLI は拒否するため、６設定群・161 入力は未測定です。

設定群ごとの `TargetRubyVersion`、ファイル種別、Regexp・Symbol・バイナリ文字列を含む Ruby の設定型を保ちます。Gemspec・Bundler の入力には必要なファイル種別を使い、`Bundler/GemFilename` と `Lint/RequireRelativeSelfPath` には名前を明示したケースも用意します。`--only` と併用できない３つのディレクティブ Cop は全 Cop で実行し、対象 Cop の記録だけを比較します。

比較前に、空でない対象パス集合の一致と全ファイルの検査完了を確認します。記録は実行ごとの多重集合とし、位置の全項目、length、メッセージ、重大度、修正可否を比較します。重複を捨てず、別の実行の逆向きの差を相殺しません。

通常の fixture テストは、593 Cop に届く記録済み 37,085 ケースを検査する別のゲートです。これが通っても、上の広い CLI 比較の代わりにはなりません。

## 残る不足

`Lint/DeprecatedReference`、`Lint/NameTypo`、`Lint/UnusedPrivateMethod` はプロジェクト索引を必要とします。sonicop はまだ全体の索引を持たないため、索引を無効にした場合の動作のみ対応しています。この掃引では発火せず、完全一致にも数えません。以前の「609 Cop すべてが発火する」という記述は誤りでした。

測定できた中で差が残るのは次の３つです。

| Cop | 入力条件 | 残る差 |
|---|---|---|
| `Lint/Syntax` | Ruby 3.3 の対象と不正な構文 | パーサの診断とエラー復帰 |
| `Style/FormatStringToken` | `Mode` に Ruby の Symbol を指定 | 過剰２件 |
| `Style/RedundantArgument` | メソッドの既定引数にバイナリ文字列を指定 | 不足１件 |

**登録数 = 発火数 = 完全一致数 = 609** が目標です。普通のアプリケーションの入力を増やすだけでは、索引が必要な動作や既定無効 Cop の被覆は増えません。

## 既定以外の設定値

設定群ごとの CLI 比較では、記録された設定を既定値へ置き換えません。今回は Ruby の Regexp タグ、旧式の除外メソッド用パターン、数値パターンのアンカー、メソッド名の許可パターン、Ruby の真偽判定、名前空間の記法、括弧付き `yield` のハッシュ値省略の差を見つけて修正しました。

YAML の型も直接検査します。Ruby が使う YAML 1.1 の引用符なし `yes`・`no`・`on`・`off` は、引用符付き文字列とは異なります。YAML 1.2 のライターで設定を作り直すと引用符が消え、検査入力そのものが変わることがあるため、該当テストは生の YAML をディスクへ書きます。引用符、明示タグ、アンカー、日本語、不正入力を陽性・陰性の両方で検査します。

表は、609 名の一覧と実行ごとの本家・sonicop の JSON を指定して `scripts/conformance_table.rb` で再生成します。未発火や差分があれば失敗し、不完全・不正なレポートは拒否します。数字を手で入力しません。
